# عقد الربط بين محرك سهم وطبقة البيانات

**الإصدار:** 1.1  
**النطاق:** `sahm-core.js` و`sahm-data.js` و`sahm-app.js` و`sahm-supabase-data.js` والواجهة الأصلية  
**المرجع الوظيفي:** `SAHM_Association_Creation_and_Installments_Reference_AR_v2.md`  
**حالة التطبيق:** المحرك ومخزن المعاينة المحلي منفصلان عن بوابة Supabase البعيدة. عند تثبيت البوابة البعيدة تكون قاعدة Supabase مصدر الحقيقة، ولا يُعامل Local Storage بوصفه قاعدة الإنتاج.

## 1. حدود المسؤولية

### `SahmCore` — محرك الحسابات

طبقة حسابية نقية لا تتعامل مع DOM أو التخزين. مسؤولة عن:
- التحقق من المبالغ والتواريخ والمنطقة الزمنية.
- تحديد مدة الدورة وتقسيم فترات الأقساط.
- توزيع المبلغ على الأقساط بوحدات العملة الصغرى الصحيحة.
- حساب الالتزامات والحالات والتأخر والانضمام المتأخر.
- حساب أهلية الأسهم للقرعة والنصاب والجائزة المستهدفة.
- التحقق من إعدادات إنشاء الجمعية.

لا تنشئ هذه الطبقة سجلات تخزين أو إشعارات أو عمليات مستخدم.

### `SahmData` — البيانات والعمليات

طبقة إدارة بيانات المعاينة، مسؤولة عن:
- تحميل البيانات وتهيئتها وترحيل الإصدارات المدعومة وحفظ نسخة أرشيفية قبل الاستبدال.
- تنفيذ العمليات المصرح بها وتسجيل الأحداث والاستلام والتصحيح والقرعة.
- توفير استعلامات موحدة تراعي دور المدير والمشارك.
- حفظ الرسائل والإشعارات والتذكيرات وتفضيلات الكتم.
- إعادة نتيجة موحدة توضح النجاح أو سبب الرفض وحالة الحفظ.

لا تمثل هذه الطبقة اتصالًا بخادم أو قاعدة بيانات مشتركة. التخزين محلي على الجهاز والمتصفح.

## 2. قواعد الحساب الملزمة

| العنصر | القاعدة |
|---|---|
| الأسبوعية | 7 أيام ثابتة |
| الشهرية | 30 يومًا ثابتة، وليست شهرًا تقويميًا |
| المخصصة | عدد صحيح من الأيام |
| أول قرعة | تاريخ البداية + مدة الدورة |
| فترات الأقساط | متتابعة وشاملة لكل أيام الدورة، دون فجوات أو تداخل |
| عدد الأقساط | لا يزيد على عدد أيام الدورة |
| توزيع المبلغ | وحدات صحيحة؛ الباقي يوزع على الأقساط الأولى |
| الحالات | `paid` و`due` و`late`؛ المستقبل يعرض `upcoming` دون اعتباره حالة تشغيلية رابعة |
| الانضمام المتأخر | تنشأ الالتزامات التي انتهت فتراتها قبل تاريخ الانضمام بوصفها متأخرة |
| الأسهم | كل سهم فرصة مستقلة؛ يستبعد السهم الفائز فقط من القرعات التالية |
| النصاب | يحسب بالأشخاص، لا بعدد الأسهم |
| القفل | أول نتيجة قرعة تثبت عدد الأسهم والجولات وتقفل إضافة الأعضاء والأسهم |
| الرسائل | رسائل الأعضاء لا تتجاوز 50 حرفًا |
| الاستلام | المدير وحده يسجل الاستلام، ويمكنه تسجيل قسطه الشخصي مع وسم التسجيل الذاتي |

## 3. وحدات المبالغ والعملات

تُخزن المبالغ في `SahmCore` و`SahmData` بوحدات العملة الصغرى الصحيحة:
- YER: الوحدة المخزنة هي الريال اليمني.
- SAR: الوحدة المخزنة هي الهللة.
- USD: الوحدة المخزنة هي السنت.

يجب أن تمر مدخلات إنشاء الجمعية عبر `SahmCore.validateGroup` ثم `SahmCore.parseMoney`. لا تستخدم الواجهة حسابًا ماليًا موازيًا ولا تحول قيمة مخزنة إلى مبلغ رئيسي دون مراعاة العملة.

## 6. نمط النتائج والأخطاء

العملية الناجحة تعيد عادةً:
```js
{ ok: true, ...result, persisted: true }
```

إذا نجحت العملية في الذاكرة وتعذر حفظها محليًا:
```js
{ ok: true, ...result, persisted: false, warning: '...' }
```

العملية المرفوضة تعيد:
```js
{ ok: false, code: 'ERROR_CODE', message: 'رسالة مفهومة' }
```

يجب على الواجهة:
1. ألا تعرض نجاحًا ماليًا أو إداريًا إذا كانت `ok` تساوي `false`.
2. أن تعرض تحذير الحفظ إذا كانت `persisted` تساوي `false`.
3. ألا تكرر حساب المبلغ أو حالة القسط أو أهلية القرعة محليًا؛ تقرأ النتيجة من المحرك والبيانات.
4. ألا تعتبر إخفاء زر في الواجهة بديلاً عن فحص الصلاحية داخل العملية.

## 7. ضوابط الصلاحيات والخصوصية

- تمرر الواجهة معرف المستخدم الحالي إلى كل استعلام يحتاج تحديد نطاق العرض.
- المدير وحده ينفذ تسجيل الاستلام والتصحيح والتذكير وإدارة الأعضاء والإعدادات والقرعة.
- المشارك يرى أقساطه وسجلاته فقط، ولا يرى رمز الدعوة أو حقول الإدارة الخاصة.
- أحداث الاستلام والتصحيح الخاصة لا تعرض للمشاركين الآخرين كسجل مالي شخصي.
- رسائل الأعضاء لا تتجاوز 50 حرفًا؛ ورسائل النظام لها قوالبها الخاصة.
- إعداد نشر إشعار المجموعة منفصل عن تفضيل كتم العضو.

## 8. حالات غير محسومة يجب عدم اختراعها

1. **تجاوز النصاب:** المرجع يحدد أن النصاب يحسب بالأشخاص، لكنه لا يقرر صراحةً وجود تجاوز إداري للنصاب. التنفيذ الحالي يقبل `overrideQuorum` في `performDraw`؛ لا تعرض الواجهة هذا الخيار ولا تعتبره قاعدة معتمدة قبل حسمه.
2. **تسجيل قسط مستقبلي:** العملية الحالية تستطيع تسجيل قسط قبل بداية فترته وتحفظ `statusAtRecord`. المرجع لا يحسم صراحةً سياسة الدفع المسبق؛ لا تضف سلوكًا أو تسمية واجهة جديدة قبل حسم القرار.
3. **تغيير إعدادات الجمعية بعد بدء الدورات:** المرجع يوصي بتثبيت إعدادات الدورات السابقة وتطبيق أي تغيير مستقبلي على دورة مستقبلية فقط؛ يجب ألا يعيد التعديل كتابة سجل تاريخي.

## 9. حدود التشغيل

- هذه نسخة معاينة محلية. لا يوجد هنا مصدر بيانات مشترك أو صلاحيات خادم أو مزامنة أجهزة أو إشعارات Push حقيقية.
- لا تعرض المعاينة تسجيل استلام بوصفه تحويلًا نفذه التطبيق أو تحققًا مصرفيًا.
- ملف HTML الحالي ما زال يحتفظ بمسارات تخزين قديمة مثل `prefs.localGroups` وبقايا واجهات إثبات الدفع. تنظيف هذه المسارات وربط كل الشاشات بالمصدر الموحد يقع ضمن الدفعة الثالثة، ولا ينبغي اعتبارها جزءًا من عقد المحرك والبيانات.
- لا تنتقل الدفعة الأولى إلى الدفعة الثانية قبل تشغيل `node --test tests/` في بيئة Node للمشروع، وإجراء تحقق تشغيل فعلي للمعاينة في Chrome، ومراجعة التقرير النهائي.

## 11. عقد التدفق الموحد — الإصدار 1.1 — 14 نوفمبر 2026

### عقد الجمعية الجديدة
- `startDate`: تاريخ بداية الدورة الأولى.
- `firstDrawOn`: تاريخ أول قرعة الصريح.
- `durationDays`: فرق الأيام المحسوب بين التاريخين للتحقق.
- `shareAmountMinor`: قيمة السهم بوحدات العملة الصغرى الصحيحة.
- `installmentMode='count'`: عدد الأقساط معلوم، ويوزع المبلغ مع إسناد الباقي إلى الأقساط الأولى.
- `installmentMode='amount'`: `installmentAmountMinor` هو القسط الثابت، وعدد الأقساط `ceil(shareAmountMinor / installmentAmountMinor)`، وآخر قسط هو المتبقي الفعلي.
- لا يتطلب العقد الحديث `targetShares` أو `maxPerMember`. تبقى الحدود التاريخية مطبقة على الجمعيات القديمة التي تحمل قيمًا فعلية.

### التقسيم والتاريخ
تقسيم الأيام والمبالغ مطابق لعقد قاعدة البيانات: الأيام الزائدة تذهب إلى الفترات الأولى، ومبالغ الباقي في وضع عدد الأقساط توزع على الأقساط الأولى، أما وضع القسط الثابت فيحفظ آخر قسط متبقٍ. الفترات متتابعة وتغطي الدورة بلا فجوات أو تداخل.

`firstDrawDate(group)` يستخدم `firstDrawOn` الصريح عند وجوده، ثم يحتفظ بالاشتقاق القديم للجمعيات السابقة. `roundDate(group, roundNo)` يحسب الجولات التالية انطلاقًا من أول قرعة الصريح.

### واجهات المحرك
- `periods(cycleDays, installmentCount)`
- `splitAmount(totalMinor, installmentCount)`
- `installmentAmounts(group)` و`shareAmounts(group)`
- `firstDrawDate(group)` و`roundDate(group, roundNo)`
- `validateGroup(input)`: يتعرف على العقد الحديث ويطبق تحقق التاريخ والمبلغ والمدة والمنطقة الزمنية، ويحتفظ بمسار الجمعيات القديمة.

### فصل الواجهة والبيانات
- `SahmData` يدير بيانات المعاينة المحلية فقط؛ تمت تهيئة `joinRequests` عند تطبيع النسخ القديمة.
- `SahmApp` هو واجهة التطبيق بين شاشات HTML وطبقة البيانات.
- `SahmSupabaseData` يحمل لقطة الجداول المحكومة بـ RLS ويثبت عمليات الكتابة عبر RPC عند تشغيل `install()`.
- إنشاء الجمعية يمر عبر `create_association_unified`، ثم محاولة إنشاء رابط عام مستقلة؛ فشل الرابط لا يطمس نجاح إنشاء الجمعية.
- الدعوات الجماعية تمر عبر `create_invitations_bulk` بحد 1–50، وتعيد نتيجة منفصلة ورابطًا لكل دعوة ناجحة.
- طلبات الانضمام تُقرأ من `join_requests` وتنعكس في `db.joinRequests`; القرار العضوي يمر عبر RPC.
- Realtime لتحديث الرسائل والإشعارات والدعوات وطلبات الانضمام، وليس لتنفيذ عملية مالية أو قرعة.

### التوافق والحدود
- الدعوات القديمة ذات عدد الأسهم تبقى في مسار قبول تاريخي منفصل.
- الرابط العام يتيح تقديم طلب ولا ينشئ عضوية مباشرة.
- العضوية والأسهم والالتزامات لا تنشأ إلا بعد موافقة المدير الذرية.
- لا توجد رسائل SMS أو WhatsApp تلقائية؛ تنشأ الروابط ويشاركها المدير من الجهاز.
- وجود ملفات الاختبار أو فحص JavaScript syntax لا يثبت صحة السلوك؛ يلزم تشغيل اختبارات Node وSQL المعزول والتحقق التشغيلي.
