# تقرير تقدم تنفيذ SAHM SUPABASE

**آخر تحديث:** 13 نوفمبر 2026  
**الفرع:** `SAHM-SUPABASE`  
**الحالة العامة:** قاعدة البيانات الأساسية والعمليات الخلفية الأولى موجودة؛ ربط الواجهة والمصادقة والاختبارات التكاملية والنشر لم تكتمل.

## 1. ما نُفذ فعليًا في مشروع Supabase

### المخطط
- أُنشئت 22 طاولة في `public`، وجميعها مفعّل عليها RLS.
- جميع الجداول فارغة من بيانات التطبيق عند آخر تحقق.
- فصل الملف العام عن `profile_private` حتى لا تظهر أرقام الهواتف للمدير أو الأعضاء.
- رقم الهاتف فريد، مع تحقق E.164 ودالة تطبيع تقبل الأرقام العربية والهندية والبادئة الدولية 00.
- المبالغ `bigint` بوحدات العملة الصغرى، والتواريخ التشغيلية `date`، والأوقات `timestamptz`.
- أضيفت فهارس مفاتيح أجنبية وفهارس استعلامات الجمعية.
- أضيف جدول Realtime للمحادثات `public.chat_messages` فقط؛ Storage غير منشأ لأنه لا توجد مرفقات في مرجع V2.

### RLS والصلاحيات
- 30 سياسة RLS مخصصة للأدوار والعلاقات.
- لا توجد منح جدولية لدور `anon`.
- منح `authenticated` للقراءة العامة محكومة بـ RLS، والكتابة المباشرة مقيدة لتفضيلات المستخدم وحالة القراءة فقط.
- بيانات الهاتف الخاصة لا يقرأها إلا صاحب الحساب، ولا يسمح بتغيير الهاتف من واجهة الحساب قبل اعتماد مسار تحقق موثوق.
- عمليات الكتابة الحساسة تنفذ عبر RPC.
- نُقلت وظائف `SECURITY DEFINER` الداخلية إلى مخطط `private` غير المكشوف، مع أغلفة `SECURITY INVOKER` في `public`. لا يستطيع `anon` تنفيذها.
- سُحبت صلاحية تنفيذ `public.rls_auto_enable()` من `anon` و`authenticated`، مع الإبقاء على محفز DDL الموجود دون حذفه.
- نتيجة Security Advisor بعد هذه المعالجة: **لا توجد ملاحظات أمنية** في آخر فحص.

### العمليات الخلفية الموجودة
الأغلفة المتاحة في مخطط `public`، وتنفيذها الفعلي المحمي داخل `private`:
- `create_association(jsonb)`
- `create_invitation(uuid,text,text,integer)`
- `accept_invitation(text)`
- `record_installment_receipt(uuid)`
- `correct_installment_receipt(uuid,text)`
- `perform_draw(uuid)`
- `set_cycle_attendance(uuid,uuid,boolean)`
- `send_chat_message(uuid,text)`
- `send_installment_reminders(uuid,integer,uuid)`
- `set_association_notification_types(uuid,text[])`
- `set_association_user_preferences(uuid,boolean,boolean)`
- `mark_my_notification_read(uuid)`

تستخدم العمليات تحقق `auth.uid()`، وتتحقق من المدير/العضوية داخل قاعدة البيانات. تسجيل الاستلام يقفل الالتزام ويمنع التكرار بقيد فريد جزئي، والتصحيح يحفظ snapshot ويحول الأصل إلى `voided` دون حذفه. القرعة تقفل الجمعية، وتستخدم عشوائية تشفيرية مع رفض الانحياز الحسابي، وتحفظ مجموعة الأسهم المؤهلة، وتستبعد السهم الفائز وحده، وتولد دورات ما بعد أول قرعة وتثبت قفل الأسهم. الرسائل النصية محددة بـ50 حرفًا. التذكير لا يغير حالة القسط.

### حفظ الأثر التاريخي
أضيفت مشغلات تمنع UPDATE/DELETE على سجل الأحداث والتصحيحات والقرعة والأسهم المؤهلة والرسائل والتذكيرات. يسمح على سجل الاستلام فقط بالانتقال من `active` إلى `voided` عبر إجراء التصحيح.

### اختبارات قاعدة البيانات التي أمكن تنفيذها
- فحص 22 جدولًا: جميعها `rls_enabled=true`.
- فحص 30 سياسة RLS.
- فحص منح الجداول: صفر امتيازات لـ`anon`؛ لا منح INSERT/DELETE عامة لـ`authenticated`.
- اختبار تطبيع رقم الهاتف: صيغة دولية، أرقام عربية، وبادئة 00 — النتائج صحيحة ومتطابقة.
- اختبار حواجز RPC دون جلسة: إنشاء جمعية/قرعة/استلام ترفض الطلب برمز `28000` «يجب تسجيل الدخول».
- فحص Security Advisor: لا توجد lints أمنية.\n- شغّلت `supabase/tests/schema_invariants.sql` على المشروع الحي، والنتيجة: `SAHM schema invariants passed`.
- Performance Advisor لا يعرض تحذيرات مفاتيح أجنبية غير مفهرسة؛ يعرض مؤشرات unused index فقط لأن الجداول جديدة وفارغة، ولا تعد هذه نتيجة فشل.

## 2. الترحيلات وسجل التغيير

- التغيير الأولي للجداول والسياسات والدوال نُفذ مباشرة عبر SQL MCP على المشروع الحي بعد التحقق من خلو مخطط `public` من جداول تطبيق. أضيفت لقطة تأسيس قابلة لإعادة الإنشاء في `supabase/SAHM_DATABASE_BASELINE.sql`. هذه لقطة baseline وليست ترحيلًا incremental، ولم تُنفذ على مشروع ثانٍ فارغ بعد؛ يجب اختبار إعادة إنشائها على بيئة نظيفة قبل اعتمادها نهائيًا.
- أول ترحيل مسجل رسميًا: `20261113195243_append_only_financial_and_audit_history`.
- ملفه في المستودع: `supabase/migrations/20261113195243_append_only_financial_and_audit_history.sql`.
- لا يجوز اعتبار سجل الترحيلات مكتملًا حتى إضافة baseline schema وتوحيد نسخة SQL المصدر مع المخطط الحي.

## 3. ما لم يكتمل بعد

1. **واجهة التطبيق:** لم يتم بعد استبدال `sahm-data.js` و`sahm-app.js` في مسار التشغيل. HTML الحالي لا يزال يعتمد LocalStorage و`me` ورمز OTP التجريبي؛ لا تستخدمه للإنتاج.
2. **Auth:** trigger إنشاء `profiles` و`profile_private` و`user_preferences` عند إدراج `auth.users` موجود. لم يُختبر عبر تسجيل Auth حقيقي؛ لم ننشئ حسابات اختبار Auth لأن أدوات الإدارة المتاحة لا توفر إنشاء حسابات Auth/تعيين كلمات مرور بأمان. لم نغير Confirm Email؛ المالك يضبطه يدويًا.
3. **عمليات غير مكتملة:** تعديل إعدادات الجمعية المالية، إدارة/إزالة الأسهم والأعضاء، قراءة حالة الدعوات/إلغائها، إدارة حالة القراءة للمحادثة، إغلاق الجمعية، وبناء الدورات الدورية/الجدولة التلقائية لم تكتمل بعد.
4. **نموذج إضافة سهم بعد تسجيل استلام سابق:** V2 يسمح بإضافة سهم قبل أول قرعة حتى لو بدأت الجمعية، لكن لا يحسم كيف يعالج النظام زيادة التزام قسط سبق تسجيل استلامه. نموذج القسط المجمع الحالي لا يسمح بتغيير الاستلام التاريخي. يلزم قرار أعمال قبل RPC إضافة الأسهم في هذه الحالة؛ لم نخترع سلوكًا.
5. **الإشعارات:** إشعارات داخل قاعدة البيانات موجودة لبعض الأحداث (الاستلام، المحادثة، التذكير)، لكن تغطية جميع أنواع الإشعار الخاصة والعامة، وقوالب النظام، والتنبيهات المجدولة وPush لم تكتمل.
6. **الاختبارات:** لم يتم تشغيل اختبارات JavaScript الـ47 ولا اختبارات المتصفح. لا توجد بعد حسابات متعددة حقيقية لإثبات عزل RLS وتزامن القرعة والاستلام.
7. **الواجهة وبيئة النشر:** لا يوجد ربط Render تجريبي مستقل ولا تم التحقق من نشر فرع العمل. لم تُمس خدمة `sahm-preview` المرتبطة بـ`main`.
8. **متغيرات البيئة:** يلزم ضبط `SUPABASE_URL` و`SUPABASE_PUBLISHABLE_KEY` (مفتاح publishable فقط للواجهة) عبر إعدادات الخدمة، لا تضمين أي secret/service_role في المتصفح.

## 4. القرارات المؤجلة

- تجاوز النصاب: لا ينفذ قبل موافقة صريحة؛ V2 لا يقره.
- السداد المسبق قبل بداية فترة القسط: غير محسوم.
- التعامل مع إضافة أسهم بعد وجود استلامات سابقة: يحتاج قرارًا صريحًا.
- Push والتذكير الآلي: يحتاجان تحديد قناة الإرسال وموافقة المالك.

## 5. طريقة الاستئناف

1. إنشاء baseline migration مطابق للمخطط الحي وتسجيله.
2. استكمال RPCs الأساسية والقيود الناقصة واختبارها.
3. بناء طبقة اتصال Supabase وAuth بالبريد وكلمة المرور.
4. تحويل كل مسارات القراءة/الكتابة في الواجهة إلى async، مع إبقاء `sahm-core.js` لمحرك الحسابات النقية.
5. إنشاء حسابات اختبار حقيقية بعد ضبط Confirm Email يدويًا، ثم اختبارات RLS متعددة المستخدمين والتزامن.
6. إعداد Preview Render مستقل بعد تأكيد مساحة العمل، دون تغيير خدمة `main`.
7. التحقق من هاتف فعلي وتوثيق commit والرابط.

**لا يعلن المشروع مكتملًا أو جاهزًا للإنتاج قبل إتمام البنود أعلاه.**


## 6. ملاحظة سلامة Git

- حدث خطأ في إحدى عمليات GitHub API: أُنشئ ملف `supabase/SAHM_DATABASE_BASELINE.sql` على `main` بسبب إغفال وسيط الفرع في استدعاء الإنشاء.
- اكتُشف الخطأ فور فحص commit، ثم حُذف الملف من `main` في commit تالٍ. التزام الإضافة: `fae934d25c2dd46fb7a14c940620c847d2e5e969`، والتزام الحذف/الاستعادة: `6e7a26bb4cb7d75fabe1a4ecd14ade21a4e46128`.
- تحقق فحص المحتويات من أن الملف غير موجود حاليًا على `main`، وأن نسخة baseline موجودة على `SAHM-SUPABASE`.
- لذلك محتوى `main` عاد إلى حالته السابقة لهذا الملف، لكن تاريخ الفرع يحتوي على التزامي الإضافة والحذف؛ لم تُجرَ إعادة كتابة قسرية للتاريخ.
- مقارنة Git الحالية: `SAHM-SUPABASE` متقدم 20 commit ومتأخر commitين عن `main`، بسبب التزامي الاستعادة أعلاه. لا يوجد Merge.
- لن تُنفذ أي كتابة أخرى على `main`.

## تحديث تنفيذي — 2026-11-13

### ما نُفذ على قاعدة Supabase الفعلية
- إضافة RPCs محمية لإدارة إعدادات الجمعية قبل بدء السجل المالي: `update_association`.
- إضافة وإزالة الأسهم مع فحص حدود الجمعية وحد العضو وقفل صف الجمعية لمنع تجاوز العدد بالتزامن: `add_shares` و`remove_shares`.
- إزالة العضو قبل بدء السجل المالي: `remove_member`.
- إلغاء الدعوة المعلقة ومعاينة الدعوة للحساب المسجل: `cancel_invitation` و`preview_invitation`.
- تحديث الاسم والمدينة من الملف الشخصي دون السماح بتعديل رقم الهاتف غير الموثق: `update_my_profile`.
- إعادة بناء فترات الأقساط والتزاماتها بعد تعديل الإعدادات أو الأسهم قبل بدء السجل، مع منع إعادة البناء بعد وجود إيصالات أو تذكيرات أو قرعات حتى لا تُمس المراجع التاريخية.
- الإبقاء على نمط RPC العام SECURITY INVOKER، مع تنفيذ منطق الأعمال في private SECURITY DEFINER، ومنح authenticated فقط صلاحية استدعاء الدوال الداخلية المطلوبة.

### التحقق
- `supabase/tests/schema_invariants.sql`: نجح على قاعدة المشروع الفعلية.
- `supabase/tests/association_rpc_invariants.sql`: نجح على قاعدة المشروع الفعلية.
- تم التحقق من وجود RPCs الجديدة، ومنع anon من معاينة رموز الدعوة، ومن عدم تحويل الأغلفة العامة إلى SECURITY DEFINER.
- لا توجد حتى الآن اختبارات تكامل عبر حساب مستخدم حقيقي؛ قاعدة Auth كانت بلا مستخدمين وقت الفحص السابق.

### ما لم يُنفذ بعد
- لا تزال واجهة HTML/JS تعتمد على SahmData/LocalStorage ولا يجوز اعتبار التطبيق متصلًا بالكامل.
- لم يُستبدل مسار OTP التجريبي بمصادقة Supabase Auth بعد.
- لم يتم ربط قراءات وكتابات الجمعيات والأعضاء والأسهم والأقساط والقرعات والمحادثات والإشعارات بقاعدة البيانات من الواجهة.
- لم يتم تغيير إعدادات Render أو نشر نسخة جديدة يدويًا في هذا التحديث؛ خدمة المعاينة مرتبطة بالنشر التلقائي من فرع SAHM-SUPABASE.
- يلزم اختبار تسجيل/دخول/تأكيد البريد مع مستخدم اختبار قبل اعتماد المصادقة على الإنتاج.

## استكمال ربط الواجهات والمصادقة — 2026-11-14

### المصادقة والملف الشخصي
- استبدال مسار OTP التجريبي بمصادقة Supabase Auth عبر البريد الإلكتروني وكلمة المرور.
- شاشة الدخول: البريد الإلكتروني وكلمة المرور، مع رابط استعادة كلمة المرور.
- شاشة إنشاء الحساب: البريد الإلكتروني، كلمة المرور، تأكيدها، وموافقة إلزامية على الشروط.
- عند إنشاء المستخدم ينشئ مشغل `auth.users` ملفًا شخصيًا غير مكتمل، دون اشتراط الهاتف قبل الدخول إلى شاشة الملف الشخصي.
- شاشة الملف الشخصي: 12 رمز حساب جاهزًا، دون رفع صور؛ الاسم الكامل من ثلاثة مقاطع؛ قائمة دولة ومفتاح اتصال بجوار الهاتف، واليمن `+967` هو الافتراضي.
- تخزين رقم الهاتف بصيغة E.164 بعد إكمال الملف، ومنع الدخول إلى الجمعية قبل اكتماله.
- إضافة استعادة كلمة المرور وتعيين كلمة جديدة مع الإبقاء على معامل رابط الدعوة عند العودة من البريد.
- إضافة صفحة `terms.html`؛ نصها مسودة تشغيلية ويحتاج مراجعة قانونية قبل اعتماد الإطلاق التجاري.

### ربط الواجهات بقاعدة البيانات
- إضافة `sahm-supabase.js` كواجهة Auth وعميل Supabase JS باستخدام publishable key فقط، دون service_role.
- إضافة `sahm-supabase-data.js` لقراءة البيانات الفعلية تحت RLS من 21 جدولًا، وتحويلها إلى نموذج البيانات الذي تستخدمه الشاشات الحالية.
- تحويل عمليات الإنشاء والتعديل والدعوات والعضوية والأسهم والأقساط والحضور والقرعة والمحادثة والإشعارات إلى RPC أو الكتابة المصرح بها من قاعدة البيانات.
- إزالة استدعاءات LocalStorage من مسار الصفحة الرئيسية الحالي؛ لا يتم عرض بيانات المعاينة المحلية كمصدر تشغيلي للمستخدم المسجل.
- إضافة صفحات قراءة مرتبة (500 صف لكل دفعة) حتى لا تتوقف القراءة عند الحد الافتراضي لعدد النتائج.
- تفعيل Realtime على رسائل المحادثة وإشعارات المستخدم مع إيقاف الاشتراك عند إنهاء الجلسة.
- إضافة ملف شروط مرتبط بنموذج التسجيل وتحديث قائمة التخزين المؤقت للتطبيق.

### ترحيلات قاعدة البيانات والاختبارات
- توحيد أسماء ملفات migrations في المستودع مع إصدارات سجل Supabase الفعلية، وإزالة النسخ المكررة ذات الأرقام غير المطابقة.
- `schema_invariants.sql`: ناجح على المشروع الفعلي (23 جدولًا وRLS على جميعها).
- `association_rpc_invariants.sql`: ناجح.
- `email_auth_profile_invariants.sql`: ناجح.
- `email_signup_profile_completion_smoke.sql`: ناجح؛ اختبارات Auth والملف الشخصي شُغّلت داخل معاملات Rollback ولم تترك مستخدمين أو بيانات تشغيل تجريبية.
- اختبار CI يتضمن وحدات Auth وطبقة البيانات والصفحات، ويحلل سكريبتات JavaScript المضمنة؛ أحدث تشغيل ناجح على الفرع: `26c2351618bf1ae6220af6ff5057e55e973337a1`.
- نشر Render لخدمة `sahm-supabase-preview-fixed` أصبح `live` على نفس Commit أعلاه.

### متطلبات خارج الكود قبل اعتماد تجربة بريد حقيقية أو إطلاق تجاري
1. إعداد Supabase Auth URL Configuration: Site URL إلى عنوان Render، وإضافة Redirect URL wildcard المطابق للنطاق حتى تقبل رسائل تأكيد البريد واستعادة كلمة المرور العودة إلى التطبيق. إعداد لوحة Auth غير متاح من أدوات إدارة المشروع المستخدمة في هذا التنفيذ.
2. فحص Security Advisor يعرض تحذيرًا واحدًا: `auth_leaked_password_protection` — حماية كلمات المرور المسربة معطّلة. يجب تفعيلها من إعدادات Auth قبل اعتماد الإطلاق.
3. يلزم اختبار تأكيد البريد وتسجيل الدخول واستعادة كلمة المرور فعليًا عبر صندوق بريد حقيقي؛ لم يُنشأ حساب إنتاجي ولم تُرسل رسائل اختبار إلى مستخدم حقيقي في هذا التنفيذ.
4. لم يتم إجراء اختبار قبول دعوة شامل بحسابين حقيقيين؛ منطق قبول الدعوة وفحص تطابق الهاتف اختُبر وفُحص داخل قاعدة البيانات.
5. رقم الهاتف يُسجل بصيغة دولية ويُطابق الدعوة، لكنه لا يصبح «موثقًا عبر SMS»؛ لم يُضف مزود SMS أو تحقق OTP للهاتف لأن تدفق التسجيل المطلوب لم يطلب ذلك.


### تحقق أخير من قاعدة المشروع الحية
- أُعيد تشغيل الاختبارات الخمسة على قاعدة Supabase الفعلية بنجاح: مخطط القاعدة، صلاحيات RPC، ثوابت Auth والملف الشخصي، إنشاء الحساب وإكمال الملف، ومسار الجمعية/الدعوة/الأسهم.
- أظهر جرد البيانات بعد الاختبارات وجود حساب مؤكد البريد وملف مكتمل، مع جمعيتين وعضويتين نشطتين ودعوة واحدة معلقة. هذه سجلات تشغيل موجودة في المشروع وليست بيانات الاختبارات ذات الأسماء والمعرّفات المؤقتة؛ تم الحفاظ عليها دون تعديل أو حذف.
- لا يوجد أي حساب تجريبي من نوع `sahm-*-rollback*@example.invalid` متبقٍ بعد الاختبارات.
- آخر CI ناجح على الفرع: `141a2b63cec7af6294ceadad29e2530503b1a696`.
- آخر Render deploy للخدمة المحددة: `live` على Commit نفسه.
- ما يزال تحذير Auth الوحيد في Security Advisor متعلقًا بتعطيل حماية كلمات المرور المسرّبة؛ يحتاج تفعيلًا من Dashboard.
