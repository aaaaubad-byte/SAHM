# تقرير تقدم تنفيذ SAHM SUPABASE

**آخر تحديث:** 13 نوفمبر 2026  
**الفرع:** `SAHM-SUPABASE`  
**الحالة العامة:** قاعدة البيانات الأساسية والعمليات الخلفية الأولى موجودة؛ ربط الواجهة والمصادقة والاختبارات التكاملية والنشر لم تكتمل.

## 1. ما نُفذ فعليًا في مشروع Supabase

### المخطط
- أُنشئت 22 طاولة في `public`، وجميعها مفعّل عليها RLS.
- جميع الجداول فارغة من بيانات التطبيق عند آخر تحقق.
- فصل الملف العام عن `profile_private` حتى لا تظهر أرقام الهواتف للمدير أو الأعضاء.
- رقم الهاتف فريد، مع تحقق E.164 ودالة تطبيع تقبل الأرقام العربية والهندية والبادئة الدولية 00.
- المبالغ `bigint` بوحدات العملة الصغرى، والتواريخ التشغيلية `date`، والأوقات `timestamptz`.
- أضيفت فهارس مفاتيح أجنبية وفهارس استعلامات الجمعية.
- أضيف جدول Realtime للمحادثات `public.chat_messages` فقط؛ Storage غير منشأ لأنه لا توجد مرفقات في مرجع V2.

### RLS والصلاحيات
- 30 سياسة RLS مخصصة للأدوار والعلاقات.
- لا توجد منح جدولية لدور `anon`.
- منح `authenticated` للقراءة العامة محكومة بـ RLS، والكتابة المباشرة مقيدة لتفضيلات المستخدم وحالة القراءة فقط.
- بيانات الهاتف الخاصة لا يقرأها إلا صاحب الحساب، ولا يسمح بتغيير الهاتف من واجهة الحساب قبل اعتماد مسار تحقق موثوق.
- عمليات الكتابة الحساسة تنفذ عبر RPC.
- نُقلت وظائف `SECURITY DEFINER` الداخلية إلى مخطط `private` غير المكشوف، مع أغلفة `SECURITY INVOKER` في `public`. لا يستطيع `anon` تنفيذها.
- سُحبت صلاحية تنفيذ `public.rls_auto_enable()` من `anon` و`authenticated`، مع الإبقاء على محفز DDL الموجود دون حذفه.
- نتيجة Security Advisor بعد هذه المعالجة: **لا توجد ملاحظات أمنية** في آخر فحص.

### العمليات الخلفية الموجودة
الأغلفة المتاحة في مخطط `public`، وتنفيذها الفعلي المحمي داخل `private`:
- `create_association(jsonb)`
- `create_invitation(uuid,text,text,integer)`
- `accept_invitation(text)`
- `record_installment_receipt(uuid)`
- `correct_installment_receipt(uuid,text)`
- `perform_draw(uuid)`
- `set_cycle_attendance(uuid,uuid,boolean)`
- `send_chat_message(uuid,text)`
- `send_installment_reminders(uuid,integer,uuid)`
- `set_association_notification_types(uuid,text[])`
- `set_association_user_preferences(uuid,boolean,boolean)`
- `mark_my_notification_read(uuid)`

تستخدم العمليات تحقق `auth.uid()`، وتتحقق من المدير/العضوية داخل قاعدة البيانات. تسجيل الاستلام يقفل الالتزام ويمنع التكرار بقيد فريد جزئي، والتصحيح يحفظ snapshot ويحول الأصل إلى `voided` دون حذفه. القرعة تقفل الجمعية، وتستخدم عشوائية تشفيرية مع رفض الانحياز الحسابي، وتحفظ مجموعة الأسهم المؤهلة، وتستبعد السهم الفائز وحده، وتولد دورات ما بعد أول قرعة وتثبت قفل الأسهم. الرسائل النصية محددة بـ50 حرفًا. التذكير لا يغير حالة القسط.

### حفظ الأثر التاريخي
أضيفت مشغلات تمنع UPDATE/DELETE على سجل الأحداث والتصحيحات والقرعة والأسهم المؤهلة والرسائل والتذكيرات. يسمح على سجل الاستلام فقط بالانتقال من `active` إلى `voided` عبر إجراء التصحيح.

### اختبارات قاعدة البيانات التي أمكن تنفيذها
- فحص 22 جدولًا: جميعها `rls_enabled=true`.
- فحص 30 سياسة RLS.
- فحص منح الجداول: صفر امتيازات لـ`anon`؛ لا منح INSERT/DELETE عامة لـ`authenticated`.
- اختبار تطبيع رقم الهاتف: صيغة دولية، أرقام عربية، وبادئة 00 — النتائج صحيحة ومتطابقة.
- اختبار حواجز RPC دون جلسة: إنشاء جمعية/قرعة/استلام ترفض الطلب برمز `28000` «يجب تسجيل الدخول».
- فحص Security Advisor: لا توجد lints أمنية.\n- شغّلت `supabase/tests/schema_invariants.sql` على المشروع الحي، والنتيجة: `SAHM schema invariants passed`.
- Performance Advisor لا يعرض تحذيرات مفاتيح أجنبية غير مفهرسة؛ يعرض مؤشرات unused index فقط لأن الجداول جديدة وفارغة، ولا تعد هذه نتيجة فشل.

## 2. الترحيلات وسجل التغيير

- التغيير الأولي للجداول والسياسات والدوال نُفذ مباشرة عبر SQL MCP على المشروع الحي بعد التحقق من خلو مخطط `public` من جداول تطبيق. أضيفت لقطة تأسيس قابلة لإعادة الإنشاء في `supabase/SAHM_DATABASE_BASELINE.sql`. هذه لقطة baseline وليست ترحيلًا incremental، ولم تُنفذ على مشروع ثانٍ فارغ بعد؛ يجب اختبار إعادة إنشائها على بيئة نظيفة قبل اعتمادها نهائيًا.
- أول ترحيل مسجل رسميًا: `20261113195243_append_only_financial_and_audit_history`.
- ملفه في المستودع: `supabase/migrations/20261113195243_append_only_financial_and_audit_history.sql`.
- لا يجوز اعتبار سجل الترحيلات مكتملًا حتى إضافة baseline schema وتوحيد نسخة SQL المصدر مع المخطط الحي.

## 3. ما لم يكتمل بعد

1. **واجهة التطبيق:** لم يتم بعد استبدال `sahm-data.js` و`sahm-app.js` في مسار التشغيل. HTML الحالي لا يزال يعتمد LocalStorage و`me` ورمز OTP التجريبي؛ لا تستخدمه للإنتاج.
2. **Auth:** trigger إنشاء `profiles` و`profile_private` و`user_preferences` عند إدراج `auth.users` موجود. لم يُختبر عبر تسجيل Auth حقيقي؛ لم ننشئ حسابات اختبار Auth لأن أدوات الإدارة المتاحة لا توفر إنشاء حسابات Auth/تعيين كلمات مرور بأمان. لم نغير Confirm Email؛ المالك يضبطه يدويًا.
3. **عمليات غير مكتملة:** تعديل إعدادات الجمعية المالية، إدارة/إزالة الأسهم والأعضاء، قراءة حالة الدعوات/إلغائها، إدارة حالة القراءة للمحادثة، إغلاق الجمعية، وبناء الدورات الدورية/الجدولة التلقائية لم تكتمل بعد.
4. **نموذج إضافة سهم بعد تسجيل استلام سابق:** V2 يسمح بإضافة سهم قبل أول قرعة حتى لو بدأت الجمعية، لكن لا يحسم كيف يعالج النظام زيادة التزام قسط سبق تسجيل استلامه. نموذج القسط المجمع الحالي لا يسمح بتغيير الاستلام التاريخي. يلزم قرار أعمال قبل RPC إضافة الأسهم في هذه الحالة؛ لم نخترع سلوكًا.
5. **الإشعارات:** إشعارات داخل قاعدة البيانات موجودة لبعض الأحداث (الاستلام، المحادثة، التذكير)، لكن تغطية جميع أنواع الإشعار الخاصة والعامة، وقوالب النظام، والتنبيهات المجدولة وPush لم تكتمل.
6. **الاختبارات:** لم يتم تشغيل اختبارات JavaScript الـ47 ولا اختبارات المتصفح. لا توجد بعد حسابات متعددة حقيقية لإثبات عزل RLS وتزامن القرعة والاستلام.
7. **الواجهة وبيئة النشر:** لا يوجد ربط Render تجريبي مستقل ولا تم التحقق من نشر فرع العمل. لم تُمس خدمة `sahm-preview` المرتبطة بـ`main`.
8. **متغيرات البيئة:** يلزم ضبط `SUPABASE_URL` و`SUPABASE_PUBLISHABLE_KEY` (مفتاح publishable فقط للواجهة) عبر إعدادات الخدمة، لا تضمين أي secret/service_role في المتصفح.

## 4. القرارات المؤجلة

- تجاوز النصاب: لا ينفذ قبل موافقة صريحة؛ V2 لا يقره.
- السداد المسبق قبل بداية فترة القسط: غير محسوم.
- التعامل مع إضافة أسهم بعد وجود استلامات سابقة: يحتاج قرارًا صريحًا.
- Push والتذكير الآلي: يحتاجان تحديد قناة الإرسال وموافقة المالك.

## 5. طريقة الاستئناف

1. إنشاء baseline migration مطابق للمخطط الحي وتسجيله.
2. استكمال RPCs الأساسية والقيود الناقصة واختبارها.
3. بناء طبقة اتصال Supabase وAuth بالبريد وكلمة المرور.
4. تحويل كل مسارات القراءة/الكتابة في الواجهة إلى async، مع إبقاء `sahm-core.js` لمحرك الحسابات النقية.
5. إنشاء حسابات اختبار حقيقية بعد ضبط Confirm Email يدويًا، ثم اختبارات RLS متعددة المستخدمين والتزامن.
6. إعداد Preview Render مستقل بعد تأكيد مساحة العمل، دون تغيير خدمة `main`.
7. التحقق من هاتف فعلي وتوثيق commit والرابط.

**لا يعلن المشروع مكتملًا أو جاهزًا للإنتاج قبل إتمام البنود أعلاه.**
