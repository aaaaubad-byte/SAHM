## 1. الغرض

تحويل المتطلبات الوظيفية في الوثيقة المرجعية إلى مسار تنفيذ عملي يغطي جميع الطبقات المرتبطة بالميزة، لا الواجهات وحدها:

1. واجهات المستخدم ومسارات التنقل.
2. منطق الأعمال والحسابات والتحقق.
3. طبقة الوصول إلى البيانات والتكامل مع Supabase.
4. مخطط PostgreSQL والجداول والقيود والفهارس.
5. دوال RPC والعمليات الذرية.
6. سياسات RLS والصلاحيات والخصوصية.
7. الإشعارات وسجل النشاط عند ارتباطهما بالمسار.
8. الاختبارات الآلية واختبارات قاعدة البيانات.
9. التوافق مع الجمعيات والدعوات والعضويات والبيانات القديمة.
10. التوثيق والتسليم والمعاينة.

الهدف هو تطوير المشروع القائم على الفرع المحدد، مع الحفاظ على بياناته ووظائفه الحالية، وتجنب إعادة البناء أو إدخال تغييرات غير مرتبطة بالنطاق.

## 2. مرجعية القرار وترتيب الأولوية

عند وجود اختلاف بين الملفات أو السلوك الحالي، يكون ترتيب المرجعية:

1. القواعد التشغيلية المعتمدة في الوثيقة المرجعية الموحدة.
2. القرارات الإضافية الصريحة لصاحب المشروع.
3. السلوك الحالي الفعلي في الكود وقاعدة البيانات، ويُستخدم لفهم التوافق لا لتجاوز المتطلبات الجديدة.
4. هذه الخطة، وهي تشرح كيفية التنفيذ ولا تنشئ قواعد عمل بديلة.

لا يجوز استنتاج قرار تجاري غير محسوم من بنية الكود القديمة. يجب توثيق المسألة وطلب حسمها قبل تنفيذ الجزء الذي يتوقف عليها.

## 3. المبادئ غير القابلة للتجاوز

- العمل على `SAHM-SUPABASE` فقط، وعدم نقل التغييرات إلى `main` دون طلب.
- فحص رأس الفرع وحالة الملفات قبل كل دفعة عمل؛ وعدم الكتابة اعتمادًا على SHA قديم.
- عدم حذف أو إعادة إنشاء بيانات أو جداول أو دوال أو سياسات قائمة لمجرد تسهيل التنفيذ.
- لا يُعد إخفاء الحقول في الواجهة تنفيذًا للمتطلب إذا ظل منطق الأعمال أو الخادم يفرض السلوك القديم.
- الدعوة وطلب الانضمام والعضوية المعتمدة كيانات ومراحل منفصلة.
- قبول الدعوة لا ينشئ عضوية ولا يثبت أسهمًا أو التزامًا ماليًا.
- لا تصبح العضوية والأسهم والالتزامات معتمدة إلا بعملية موافقة المدير الناجحة.
- الطلب المعلق أو المرفوض أو الملغى لا يدخل في إجمالي الأسهم المعتمدة.
- لا يحدد المدير أسهم المدعو؛ يحدد مقدم الطلب عدد الأسهم، ويوافق المدير على العدد المطلوب كاملًا أو يرفض الطلب.
- الرابط العام قناة لتقديم طلب، وليس وسيلة لإنشاء عضوية تلقائية.
- جميع قواعد الصلاحية والتوقيت ومنع التكرار تُفرض في الخادم وقاعدة البيانات، لا في الواجهة وحدها.
- كل عملية مالية أو عضوية حساسة يجب أن تكون آمنة عند التكرار وإعادة المحاولة والتزامن.
- الحفاظ على مسارات البيانات القديمة، مع فصل المسار الجديد عند الحاجة بدل كسر القديم.
- لا تستخدم بيانات تجريبية ثابتة لتقديم الوظيفة على أنها متصلة بقاعدة البيانات الحقيقية.
- أي وظيفة غير متاحة خلفيًا يجب تمييزها بوضوح وعدم الادعاء بأنها تعمل.
- لا تُطبّق migrations على قاعدة Supabase النشطة ضمن إعداد الخطة أو التطوير؛ تُراجع أولًا ويُطلب اعتماد صريح مستقل قبل التطبيق.

## 4. خط الأساس الذي يجب تثبيته قبل التعديل

المعلومات التالية تمثل خط الأساس الذي ظهر في الفحص السابق، ويجب إعادة التحقق منها من الفرع وقاعدة البيانات عند بدء التنفيذ، لأنها قد تتغير:

- المستودع: `aaaaubad-byte/SAHM`.
- الفرع: `SAHM-SUPABASE`.
- آخر رأس معروف وقت إعداد الخطة: `584dcd1f33066bd37d3c629d9e63cea58af2c068`.
- ملف المواصفات: `docs/SAHM-UNIFIED-ASSOCIATION-FLOW-SPEC.md`.
- مشروع Supabase المرجعي: `nusjnnrtpxbpphphmdsc`.
- قاعدة البيانات ليست فارغة، وتحتوي جمعيات وعضويات ودعوات وأسهمًا وملفات مستخدمين قائمة.
- سبق رصد 23 جدولًا عامًا مع تفعيل RLS عليها، و12 migration مطبقة؛ يجب إعادة التحقق وعدم التعامل مع الأرقام كقيود ثابتة.
- توجد عمليات حالية مثل `create_invitation` و`accept_invitation` مرتبطة بسلوك الدعوة القديم.
- جدول `invitations` يتضمن `shares_requested` إلزاميًا في النموذج القديم.
- مسار قبول الدعوة الحالي ينشئ عضوية وأسهمًا مباشرة، وهو غير مطابق لمسار الطلب ثم الموافقة.
- قيود `associations` الحالية تتضمن حقولًا وقيودًا مرتبطة بنوع الدورة والعدد المستهدف والحد الأقصى للفرد.
- يوجد قيد فريد معروف على `(association_id, user_id)` في `association_memberships`، ويجب تحليل أثره على إعادة الانضمام.

هذه النقاط ليست بديلًا عن فحص المخطط الفعلي، ولا يجوز إنشاء migration اعتمادًا عليها وحدها.

## 6. مراحل التنفيذ وبوابات الاعتماد

### المرحلة 0 — إعادة التحقق من الفرع والبيئة

**الأعمال:**
- التحقق من المستودع والفرع الحاليين ورأس الفرع.
- فحص وجود تغييرات أو ملفات غير متوقعة وعدم استبدالها.
- جلب قائمة الملفات وبنية المشروع الفعلية.
- قراءة الوثيقة المرجعية كاملة ومراجعة آخر التغييرات ذات الصلة.
- التحقق من اتصال GitHub وSupabase وصلاحيات القراءة والكتابة.
- التحقق من migration history والمخطط الحالي دون إجراء أي كتابة على قاعدة الإنتاج.

**المخرجات:**
- تقرير خط أساس مؤرخ.
- قائمة الملفات الفعلية ذات الصلة.
- قائمة migrations المطبقة والموجودة في الفرع.
- قائمة الفروقات والمخاطر قبل التطوير.

**بوابة الانتقال:** لا يبدأ تعديل الكود أو المخطط قبل التأكد من الفرع والبيئة وعدم وجود تعارضات غير مفهومة.

### المرحلة 1 — تحليل العقود وتثبيت قواعد الأعمال

**الأعمال:**
- رسم دورة حياة الدعوة من الإنشاء حتى الرد أو الإلغاء.
- رسم دورة حياة طلب الانضمام من التقديم حتى الإلغاء أو الرفض أو الموافقة.
- تعريف الحالات والانتقالات المسموحة لكل كيان.
- تعريف الصلاحيات: المدير، مقدم الطلب، المدعو، العضو، والزائر عبر الرابط العام.
- تعريف مصادر الحقيقة لكل معلومة: قاعدة البيانات، RPC، أو قيمة محسوبة.
- توثيق عقود المدخلات والمخرجات والأخطاء لكل عملية.
- تتبع حساب الأسهم والالتزامات والأقساط إلى التنفيذ الحالي قبل تحديد أي تغيير.
- تحديد سياسة إعادة التقديم بعد الرفض أو الإلغاء.
- تحديد سلوك الدعوات القديمة التي تحتوي أسهمًا.
- تحديد أثر وجود عضوية سابقة أو مغادرة سابقة للشخص نفسه.
- تحديد طريقة حساب أول قرعة ومدة الدورة والمنطقة الزمنية وفق الوثيقة المرجعية.

**المخرجات:**
- مخطط حالات وانتقالات.
- مصفوفة صلاحيات.
- عقود RPC وطبقة البيانات.
- سجل قرارات مفتوحة لا تُحسم بالتخمين.

**بوابة الانتقال:** حسم القرارات التي تؤثر في المخطط أو الحسابات أو العضوية قبل اعتماد تصميم قاعدة البيانات.

### المرحلة 2 — تصميم قاعدة البيانات والعمليات الخلفية

**الأعمال:**
1. مقارنة المتطلبات بالمخطط الحالي لتحديد ما يمكن إعادة استخدامه.
2. تصميم تمثيل مستقل لطلبات الانضمام إذا ثبت عدم وجود كيان مناسب قابل لإعادة الاستخدام.
3. تصميم تمثيل للرابط العام وحالة تشغيله وتجديده وإبطاله، إذا لم توجد بنية مناسبة.
4. معالجة التوافق بين الدعوات القديمة والجديدة دون فقد بياناتها.
5. معالجة إلزامية `invitations.shares_requested` القديمة بطريقة انتقالية آمنة؛ لا تحذف العمود أو القيد قبل إثبات عدم اعتماد أي مسار قديم عليه.
6. مراجعة قيود `associations` المتعلقة بـ `target_shares` و`max_shares_per_member` ونوع الدورة ومدة الدورة، ووضع خطة توافق تحفظ صفوف الجمعيات القديمة.
7. تصميم عمليات خادمية منفصلة لتقديم الطلب وإلغائه ومراجعته والموافقة عليه أو رفضه والرد على الدعوة وإدارة الرابط العام.
8. جعل الموافقة عملية ذرية واحدة تشمل التحقق من الصلاحيات والحالة والموعد، وإنشاء/تفعيل العضوية، واعتماد الأسهم، وإنشاء الالتزامات، وتحديث الطلب، وتسجيل الحدث المرتبط.
9. حماية العمليات من النقر المكرر وإعادة إرسال الطلب والتزامن.
10. استخدام قفل مناسب أو آلية تنافس آمنة عند اعتماد طلبين متزامنين للشخص نفسه أو عند الاقتراب من إغلاق الانضمام.
11. حفظ رمز الرابط العام بصيغة آمنة، وعدم تخزين سر قابل للاستخدام كنص مكشوف إذا لم تكن هناك ضرورة موثقة.
12. فرض تاريخ إغلاق الانضمام على الخادم وفق المنطقة الزمنية للجمعية، عند 23:59:59 من اليوم السابق لبداية الجمعية كما تحدد الوثيقة المرجعية.
13. مراجعة سياسات RLS وعمليات `SECURITY DEFINER` و`search_path` والمنح بعناية.
14. إضافة فهارس وقيود تمنع الحالات المتعارضة والتكرار حيث يلزم.
15. توفير مسار ترحيل للبيانات القديمة دون إسقاط أو تعديل تدميري.

**أسماء عمليات مرشحة للتصميم، وليست عقودًا نهائية قبل فحص الموجود:**
- `submit_join_request`
- `cancel_join_request`
- `list_join_requests`
- `get_join_request`
- `approve_join_request`
- `reject_join_request`
- `respond_to_invitation`
- عمليات إنشاء/عرض/تشغيل/إيقاف/تجديد/إبطال الرابط العام.

يجب فحص RPC الحالية وإعادة استخدام ما يناسب، وعدم إنشاء أسماء أو واجهات متكررة بلا داعٍ. ولا يُفترض أن `accept_invitation` تصلح للموافقة على طلب انضمام؛ يُحافظ على توافقها مع الاستخدام القديم أو يُستبدل مسارها بخطة انتقالية موثقة.

**المخرجات:**
- تصميم مخطط قبل/بعد.
- migrations صغيرة مرتبة وقابلة للمراجعة.
- وصف التوافق والرجوع.
- اختبارات SQL invariants وRLS.
- قائمة بالتغييرات التي تحتاج قرارًا وظيفيًا فقط، وأثر أي حذف/ترحيل ضروري على البيانات القديمة.

**بوابة الاعتماد:** إعداد migrations في Git لا يعني تطبيقها. التطبيق على مشروع Supabase المحدد مفوض ضمن هذا النطاق؛ لا تطلب موافقة مستقلة لكل migration. أوقف الجزء المتأثر فقط إذا ظهر حذف غير مرتبط بالمواصفات أو تعارض بيانات لا يمكن الحفاظ عليه بأمان.

### المرحلة 3 — منطق الأعمال وطبقة البيانات

**الأعمال:**
- فصل منطق الدعوة عن منطق طلب الانضمام وعن اعتماد العضوية.
- تعديل حساب مدة الدورة وفق التواريخ المعتمدة، دون كسر تفسير سجلات الجمعيات القديمة.
- احتساب الإجماليات من الأسهم المعتمدة فقط.
- استبعاد الدعوات والطلبات المعلقة والمرفوضة والملغاة من أرقام العضوية والأسهم.
- حساب الالتزام المالي وعرضه وفق القواعد المعتمدة، مع عدم جعل حساب الواجهة مصدرًا نهائيًا للمبلغ.
- تحديث adapters وواجهات RPC في `sahm-supabase-data.js` وأي وحدات ذات صلة.
- توحيد معالجة الأخطاء وحالات انتهاء الرابط وإغلاق الانضمام وتعارض الحالة.
- توفير تحديث بيانات موثوق بعد الإرسال والموافقة والرفض والإلغاء.
- منع استخدام بيانات محلية أو mock بدل Supabase في المسار الفعلي.
- الحفاظ على مسارات قراءة البيانات القديمة.

**المخرجات:**
- وحدات منطق أعمال قابلة للاختبار.
- طبقة بيانات متوافقة مع عقود RPC المعتمدة.
- معالجة واضحة لحالات النجاح والفشل وإعادة المحاولة.

### المرحلة 4 — التنقل والواجهات

يتم تطوير الواجهات على مراحل صغيرة، مع المحافظة على الهوية البصرية وRTL والخطوط والمكونات الحالية.

**4.1 إنشاء الجمعية**
- اختصار الإنشاء إلى شاشتين رئيسيتين وفق المواصفات.
- إدخال تاريخ البداية وأول قرعة.
- حساب مدة الدورة تلقائيًا.
- إزالة العدد المستهدف للأسهم والحد الأقصى لأسهم الفرد من تجربة الإنشاء الجديدة.
- المحافظة على بيانات المدير والمساهمة والقواعد التي تقرها الوثيقة.

**4.2 نجاح الإنشاء واستقبال الأعضاء**
- جعل شاشة النجاح نقطة انطلاق لاستقبال الأعضاء.
- عرض الرابط العام وإجراءات نسخه ومشاركته وإدارته عندما يكون مدعومًا بالخلفية.
- توفير مدخل واضح لإدارة الدعوات وطلبات الانضمام.

**4.3 جهات الاتصال والدعوات**
- البحث والتحديد المتعدد لجهات الاتصال.
- إزالة تحديد الأسهم من نموذج الدعوة الجديدة.
- منع الدعوات الفعالة المكررة وفق قواعد الهوية المعتمدة.

## 9. القرارات المفتوحة الواجب حسمها

هذه نقاط لا يجوز حسمها بالتخمين. يجب فحص الكود والوثيقة ثم طلب قرار صاحب المشروع إذا بقيت غير محددة:

1. **قيمة القسط:** هل المدخل يمثل قيمة القسط للسهم الواحد أم إجمالي التزام العضو؟ وكيف يوزع أي باقي إذا لم تنقسم القيمة بالتساوي على عدد الأقساط؟
2. **العضوية السابقة:** إذا غادر شخص جمعية ثم قدم طلبًا جديدًا، هل يعاد تفعيل سجل عضويته السابق مع حفظ التاريخ، أم يمنع من الانضمام مجددًا، أم يُنشأ سجل جديد وفق نموذج تاريخي؟
3. **الطلبات المتعددة:** ما السياسة الدقيقة عند وجود طلب سابق مرفوض أو ملغى ثم طلب جديد، وما الذي يحدث إذا وجد طلبان متزامنان؟
4. **أول قرعة ومدة الدورة:** هل تاريخ أول قرعة هو المرجع المباشر لحساب مدة الدورة، وكيف يُفسر ذلك مع حقول `cycle_type` و`cycle_days` القديمة؟
5. **الدعوات القديمة:** كيف تُعرض الدعوة القديمة التي تحتوي `shares_requested` دون تقديمها على أنها طلب عضوية أو أسهم معتمدة؟
6. **الإشعارات:** ما أنواع الإشعارات التي يدعمها النظام الحالي، وهل يلزم توسيع البنية أم يكفي ربط الأحداث الحالية؟

يجب أن يحتوي سجل القرار على السؤال، والخيارات، والأثر على الواجهة والكود والمخطط، والقرار النهائي وتاريخه.

## 10. استراتيجية migrations وحماية البيانات

- كل تغيير في قاعدة البيانات يكون migration جديدًا مستقلًا ومرقمًا وفق النمط المعتمد في المشروع.
- لا تعدّل migration مطبقة سابقًا لإعادة كتابة التاريخ.
- لا تستخدم `SAHM_DATABASE_BASELINE.sql` كبديل عن migration لقاعدة نشطة؛ هذا الملف مخصص لتهيئة قاعدة جديدة بعد التأكد من الغرض الفعلي منه.
- استخدم تغييرات إضافية وانتقالية قدر الإمكان: إضافة أعمدة أو جداول أو دوال، ثم نقل القراءة والكتابة، ثم إزالة الاعتماد القديم فقط بعد إثبات عدم استخدامه واعتماد ذلك.
- لا تحذف أعمدة أو قيودًا أو دوال قديمة ضمن دفعة واحدة مع إضافة البديل.
- أضف اختبارات تثبت بقاء بيانات الجمعيات القديمة قابلة للقراءة والعمل.
- وثّق خطة rollback وحدودها؛ بعض عمليات البيانات لا يمكن التراجع عنها بمجرد عكس DDL.
- تُراجع migrations وقيودها قبل التطبيق على القاعدة المرتبطة؛ وتؤجل كتابة وتشغيل الاختبارات الشاملة إلى ما بعد اكتمال التطوير.
- افحص RLS والمنح وملكية الدوال وخصائص `SECURITY DEFINER` و`search_path` قبل اعتماد كل عملية.
- لا تُرسل أسرار أو مفاتيح Supabase إلى المستودع أو السجلات أو وثائق التنفيذ.
- تطبيق migrations على مشروع Supabase المرتبط مفوض ضمن التوجيه الحالي؛ افحص المشروع والفرع والمخطط قبل التطبيق، واحفظ كل migration في المستودع وسجل نتيجة تطبيقها.

## 13. صيغة تقرير كل دفعة

يجب أن يتضمن تقرير كل دفعة:

1. رقم الدفعة وهدفها.
2. الملفات التي تمت قراءتها.
3. الملفات التي أضيفت أو عُدلت.
4. ملخص التغيير وأسبابه.
5. أثر التغيير على الواجهة ومنطق التطبيق وSupabase.
6. الاختبارات التي شُغلت ونتائجها الفعلية.
7. migrations الجديدة وحالتها: أُنشئت فقط / اختُبرت على بيئة معزولة / طُبقت بعد اعتماد مستقل.
8. المشكلات أو القرارات المفتوحة.
9. commit SHA ورابطه عند إنشاء commit.
10. ما تبقى قبل الانتقال إلى الدفعة التالية.

لا تستخدم عبارات مثل «تم الربط» أو «تم الاختبار» إلا إذا نُفذت العملية وتحقق نجاحها فعليًا.

## 14. تعليمات البدء

عند بدء التنفيذ الفعلي:

1. أعد فحص رأس `SAHM-SUPABASE` وتأكد من أنه الفرع المستهدف.
2. اقرأ الوثيقة المرجعية وهذه الخطة والملفات الفعلية ذات الصلة.
3. أعد فحص قاعدة البيانات للقراءة فقط، وسجل migration history والمخطط وRLS.
4. لا تبدأ بالواجهات قبل فهم عقود البيانات والحالات، ولا تبدأ بتغييرات قاعدة البيانات قبل تحديد التوافق.
5. نفّذ الدفعات تدريجيًا مع اختبارات وcommits موثقة.
6. لا تدمج إلى `main`.
7. تطبيق migrations على مشروع Supabase `nusjnnrtpxbpphphmdsc` مفوض ضمن نطاق هذا التنفيذ. حافظ على البيانات القائمة، ولا تحذف إلا ما يفرضه المرجع بعد فحص أثره؛ لا تنفذ تصفيرًا أو حذفًا عامًا.
8. عند وجود قرار تجاري غير محسوم، أوقف الجزء المتأثر فقط، ووثق السؤال وأثر الخيارات بدل اختراع إجابة.
