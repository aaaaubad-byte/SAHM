## 2. العناصر القديمة المؤكدة التي عولجت

### أسماء شاشات مصادقة متقادمة
كانت دالتا إظهار/إخفاء الشريط العلوي والتنقل السفلي تحتويان قائمتين محليتين تستثنيان `phone` و`otp` رغم عدم وجودهما ضمن `AUTH_SCREEN_NAMES` أو `ALL_SCREEN_REGISTRY`. كما لم تكن القائمتان متطابقتين مع الشاشات الفعلية، ما يترك اختلافاً في سلوك `account-login` و`reset-password`.

الإجراء:
- توحيد مصدر الحقيقة إلى `AUTH_SCREEN_NAMES`.
- استخدامه في `renderTopbar` و`syncBottomNavigation` و`render`.
- إضافة اختبار عقد يمنع عودة أسماء الشاشات القديمة أو قوائم الاستثناء المنسوخة.

### وثائق تشغيل قديمة ومضللة
- `SAHM_RESUME_DIRECTIVE.md` كانت تقول إن المراحل 2–6 لم تبدأ، وتحتوي تعليمات تنفيذ SQL أصبحت تاريخية.

الإجراء:
- الإبقاء على الوثائق كسجل تاريخي وعدم حذف سجل القرارات.
- إضافة تحذير واضح في أعلاها يبين أنها ليست مصدر الحالة الحالي، ويمنع إعادة تنفيذ تعليمات SQL القديمة دون مراجعة.

## 3. عناصر لم تُحذف لأنها ليست ميتة

- `wall` هي قائمة محادثات الجمعيات، بينما `chat` محادثة جمعية محددة؛ ليستا شاشة مكررة.
- `news` موجز أخبار الجمعية، بينما `audit` سجل تدقيق المدير؛ اختلاف صلاحيات ومحتوى.
- `draw-room` و`draw-history` لكل منهما غرض مستقل: تشغيل/عرض القرعة مقابل المحاضر المحفوظة.
- مسار الدعوات القديمة `legacy invitation` ما زال له مسارات UI وRPC واختبارات وتوافق تاريخي؛ لا يمكن اعتباره كوداً ميتاً.
- `sahm-data.js` محرك معاينة محلي/اختبارات، وليس نسخة إنتاجية زائدة يمكن حذفها دون مراجعة وضع التشغيل المحلي.
- `sahm-navigation.js` و`sahm-app.js` وطبقتا البيانات ملفات محملة فعلياً من HTML؛ لا تحذف اعتماداً على عدد المراجع النصية فقط.
- ملفات migrations وSQL tests وسجل baseline تاريخية/تشغيلية؛ لا تُحذف لمجرد أن واجهة المنتج لا تستدعيها مباشرة.

## 4. جرد التبعيات

- `index.html` يحوّل إلى `Sahm_Preview_ROLE_SEPARATION.html`.
- HTML يحمل `manifest.webmanifest` وأيقونة `icons/sahm.svg` ومكتبة Supabase وملفات JavaScript الستة.
- `sw.js` يضيف ملفات التشغيل نفسها إلى app shell ويدير إصدارات cache.
- تم فحص أسماء دوال JavaScript المعلنة في ملفات التشغيل السبعة؛ لم يظهر اسم دالة معلن بمرة واحدة فقط في نطاق البحث الساكن. هذا لا يثبت عدم وجود كود ميت داخل closures أو خصائص ديناميكية.
- يوجد سجل مركزي للشاشات `ALL_SCREEN_REGISTRY`، واختبار عقد يفحص تسجيل الشاشات ومساراتها.
- لا يمكن إعلان CSS class أو DOM id ميتاً اعتماداً على البحث النصي البسيط وحده بسبب HTML الذي يُبنى ديناميكياً.

## 5. التغييرات المنفذة في هذه الدفعة

1. توحيد قوائم شاشات المصادقة على `AUTH_SCREEN_NAMES` بدلاً من قوائم محلية قديمة ومتعارضة.
2. إضافة اختبار عقد للتحقق من القائمة المركزية ومنع عودة `phone` و`otp` كأسماء شاشات.
3. وسم وثائق الاستئناف وخطة الفجوات وملخص سجل التقدم بأنها لقطات تاريخية حتى لا تستخدم كتعليمات حالية.

## 6. ما بقي ويتطلب تدقيقاً قبل الحذف

- بناء خريطة استخدام كاملة لكل شاشة من كل `data-go` و`data-action` ونتائج RPC وRealtime، ومقارنة صلاحيات المدير/المشارك.
- تحليل أزرار وعناصر الواجهة الديناميكية التي تنشأ من template strings، مع التحقق من وجود handler لكل action.
- تدقيق API لكل من `SahmCore` و`SahmApp` و`SahmData` و`SahmSupabaseData` ومقارنة exports بمستهلكيها واختباراتها.
- تحديد المسارات المحلية والقديمة التي يمكن إيقافها بعد إثبات عدم استخدامها في التشغيل والاختبارات والترحيل.
- اختبار بصري حي للهاتف وسطح المكتب قبل حذف قواعد cascade أو دمج مكونات تؤثر في الشكل.
- تشغيل SQL tests المعزولة عند توفر بيئة اختبار مناسبة، دون تطبيق أي تغيير على قاعدة البيانات الحية.
- فحص assets وPWA cache وإصداراتها بعد اكتمال تغييرات الملفات.

## 7. التحقق من التنفيذ

- توحيد قواعد إظهار الشريط العلوي والتنقل السفلي على `AUTH_SCREEN_NAMES`؛ أزيلت إحالات أسماء الشاشات القديمة `phone` و`otp` من تلك القواعد.
- إضافة اختبار عقد يمنع عودة القوائم المحلية القديمة ويؤكد الشاشات الست للمصادقة.
- GitHub Actions على commit `036cc47dc1b3fa2f4b91636e017fc7e8f04e08c1`: **128 اختباراً ناجحاً، 0 فشل**.

- لا توجد إحالات حالية إلى `phone` و`otp` كأسماء شاشات في قوائم إظهار/إخفاء التنقل.

## 8. ما لم يتم

## 1. ملخص تنفيذي

تمت مراجعة سجل الشاشات المركزي وقوالب العرض ومسارات التفاعل في نسخة الفرع المحددة. سجل التطبيق يحتوي **32 شاشة** مسجلة، ولا توجد ضرورة لحذف شاشات وظيفية لمجرد تقارب أسمائها. ظهرت مشكلات استخدام وربط واضحة في البحث، وتكرار زر الإنشاء، ومعنى إجراء إدارة الرابط، وإظهار بعض الروابط حسب الدور، وتحديد العنصر النشط في الشريط السفلي.

كما تأكد وجود ازدواج في خدمات النشر: خدمتان لفرع العمل نفسه تنشران commit واحداً، وخدمة معاينة أقدم تتبع فرع main. هذا يستدعي حسم الرابط الرسمي الذي يستخدمه الفريق قبل تفسير أي اختلاف بين النسخ المنشورة.

**الاستنتاج:** المشروع لا يحتاج إعادة بناء شاملة للشاشات؛ الأولوية إصلاح نقاط الدخول والإجراءات المتكررة، ثم توحيد مسارات استقبال الأعضاء، ثم تحسين إدارة الجمعية والتفاعلات، مع الحفاظ على فصل الوظائف الحالية وعلى حماية القرعة المالية في قاعدة البيانات.

### الشاشات التي لا ينبغي دمجها

- قائمة الدردشات wall ومحادثة chat: الأولى اختيار الجمعية، والثانية محادثة جمعية محددة.
- أخبار الجمعية news والإشعارات الشخصية notifications وسجل المدير audit: ثلاثة نطاقات مختلفة من الجمهور والخصوصية والغرض.
- غرفة القرعة draw-room وسجل القرعة draw-history: الأولى تنفيذ ومراقبة الجاهزية، والثانية مرجع تاريخي للنتائج.
- الأقساط installments وسجلات الاستلام receipts: الأولى التزامات مستحقة وحالاتها، والثانية إثباتات تسجيل الاستلام والتصحيحات.
- الدعوات invites وطلبات الانضمام join-requests: الدعوة الخاصة ليست طلب الانضمام العام، ولكل منهما دورة حياة مختلفة.
- تفاصيل الدعوة القديمة invite-detail لا تُحذف قبل حسم انتهاء التوافق مع الدعوات القديمة واختبار مساراتها.

### تفصيل مهم لإدارة الرابط العام

راجعت واجهة المستخدم مع دالة SQL الخاصة بإدارة الرابط. الخادم يفرض قيد استقبال الأعضاء على عمليات create وrotate وresume، لكنه يسمح للمدير بتنفيذ pause وrevoke حتى بعد إغلاق الانضمام. الواجهة الحالية تربط ظهور منطقة الرابط بالكامل بصلاحية canInvite، ولذلك تخفي أيضاً إجراءَي الإيقاف والإبطال المشروعين. الإصلاح يجب أن يعكس هذا الفصل، لا أن يخفف حراسة الخادم.

كما أن إجراء rotate يلغي الرابط السابق ويصدر رمزاً جديداً؛ لذلك لا ينبغي إطلاقه من زر يحمل معنى عاماً مثل «إدارة الرابط» من دون تأكيد أو عرض أثره على الرابط القديم.

## 5. التمييز بين التكرار الحقيقي والتشابه الوظيفي

### تكرار يحتاج إلى إزالة أو دمج
- زر إنشاء الجمعية في toolbar وداخل empty state.
- تكرار نقاط الوصول إلى دعوة عضو وإدارة الدعوات وطلبات الانضمام في عدة مساحات دون تسلسل موحد.
- إعادة عرض أدوات إدارة الرابط واستقبال الأعضاء في صفحة نجاح الإنشاء ثم داخل تفاصيل الجمعية.
- النصوص المتكررة حول الرابط ونسخه ومشاركته وإدارته؛ ينبغي أن تكون لكل حالة تسمية وإجراء واحد واضح.

### تشابه يجب الحفاظ عليه
- news وnotifications وaudit ليست نسخاً متكررة؛ تختلف في النطاق والخصوصية.
- wall وchat ليستا تكراراً؛ تختلفان في قائمة المحادثات والمحادثة المحددة.
- draw-room وdraw-history ليستا تكراراً؛ تختلفان في التنفيذ والتاريخ.
- installments وreceipts ليستا تكراراً؛ تختلفان في الالتزام وإثبات التحصيل.
- local data وSupabase data طبقتان بواجهتين مختلفتين للمعاينة المحلية والتشغيل البعيد، وليستا نسختين زائدتين.
- مسار legacy invitation ما زال متصلاً بقوالب وتوافق واختبارات؛ لا يحذف قبل إثبات انتهاء البيانات والمسارات القديمة.

## 6. نتيجة مراجعة إنشاء الجمعية والقرعة

### إنشاء الجمعية
نموذج الإنشاء الحالي مقسم إلى خطوتين، ويتضمن تاريخ البداية وأول قرعة واشتقاق المدة، ثم بيانات الجمعية والعملة وقيمة السهم وطريقة/عدد الأقساط ومشاركة المدير وعدد أسهمه. هذه البنية تؤدي وظيفة فعلية، لذلك لا أوصي بإعادة كتابتها من الصفر ضمن حملة إزالة التكرار. الأولوية مراجعة ترتيب المدخلات والتسميات والمعاينة وتقليل ما يطلب من المدير دون تغيير الحسابات أو عقود الإنشاء في الخادم.

شاشة النجاح ينبغي ألا تصبح لوحة إدارة ثانية. الأفضل تأكيد نجاح، ملخص أساسي صغير، رابط الانضمام العام مع النسخ/المشاركة، ثم انتقال واضح إلى الجمعية.

### القرعة
المراجعة أكدت أن فصل غرفة القرعة عن السجل صحيح ويجب الحفاظ عليه. كما أكدت أن حماية الجاهزية لا تعتمد على زر الواجهة وحده:
- واجهة المدير تعرض الجاهزية المالية وتفاصيل المبالغ وعدد الالتزامات/الأسهم المكتملة.
- زر التنفيذ يعطل في الواجهة حين تكون الجاهزية غير مكتملة.
- دالة التنفيذ في PostgreSQL تتحقق مرة أخرى من دور المدير ورقم الجولة وموعد الاستحقاق والوقت المحدد.
- دالة الجاهزية تتحقق من الفترات المتوقعة، ووجود التزامات كل عضوية وأسهمها، ومطابقة المبالغ، وعدم وجود التزامات يتيمة، ومطابقة الإيصالات، واكتمال السداد ضمن النطاق التراكمي حتى الجولة المستهدفة.
- عند عدم الجاهزية يرفض الخادم تنفيذ القرعة.

**شرط الحفاظ:** لا تضعف الفحص التراكمي ولا تنقله إلى المتصفح. يجب أن يبقى قرار أهلية القرعة النهائي على قاعدة البيانات. ويجب أن تبقى شاشة التاريخ للقراءة فقط، ولا تسمح بتعديل نتيجة مثبتة.

## 7. مراجعة الأدوار والخصوصية

- شاشة الأعضاء والدعوات والطلبات وسجل التدقيق محصورة في مسار المدير في الواجهة.
- العضو يرى التزاماته وتقدمه، ويصل إلى القرعة والنتائج وسجلات الاستلام والمحادثة والأخبار.
- الموافقة على طلب الانضمام تتوقف عندما يغلق الاتفاق؛ الرفض يظل متاحاً في حالة الطلب المعلق، وهو سلوك ينبغي أن يظل واضحاً للمستخدم.
- سجل التدقيق الإداري مقيد في الخادم بالمدير؛ أما موجز الأخبار فيعرض نسخة مهيأة للأعضاء وتُحسم رؤية اسم صاحب الحدث وفق إعدادات النشر.
- الإشعارات الشخصية منفصلة عن موجز أخبار الجمعية.
- لا يكفي إخفاء الأزرار في الواجهة وحده لإثبات حماية البيانات؛ يجب أن تستمر اختبارات RLS وRPC للتحقق من الصلاحيات الفعلية.

## 8. أحداث الواجهة وبقايا الربط

اختبار العقد الحالي يتحقق من أن الأزرار لها مسار أو إجراء، وأن المسارات الثابتة موجودة في سجل الشاشات، وأن نماذج الإرسال مغطاة بمعالج. هذا اختبار مهم لكنه لا يثبت أن كل عنصر يقدم السلوك الصحيح. مثال واضح: حقلا groupSearch وmemberSearch موجودان ولا يظهر لهما مستمع input، بينما inviteeSearch موصول فعلياً بتصفية قائمة المدعوين.

لذلك يجب توسيع اختبارات العقد في دفعة الإصلاح لتشمل:
- وجود مستمع بحث لكل حقل بحث ظاهر، وتغير النتائج فعلياً.
- اختبار تبويب الشريط النشط على كل مجموعة شاشات.
- تطابق العناصر الظاهرة مع أدوار المدير والمشارك وحالة قفل الاتفاق.
- سلوك زر إدارة الرابط بحيث لا ينفذ rotate مباشرة.
- عدم عرض رابط audit للمشارك.
- عدم وجود عناصر أو مستمعات orphan مثل bioToggle وgroup-tab بعد التنظيف.
- توثيق الأزرار التي تتشارك إجراءً واحداً بشكل مقصود بدلاً من اعتبارها تكراراً آلياً.

## 11. قائمة الإصلاحات النهائية حسب الأولوية

### الدفعة الأولى — إصلاحات مباشرة عالية الأولوية
1. فصل وجهتي «جمعيات أديرها» و«جمعيات أشارك فيها» على مستوى التنقل والعنوان مع إعادة استخدام مكوّن القائمة.
2. إزالة زر إنشاء الجمعية المكرر والإبقاء على موضع واحد.
3. توصيل بحث الجمعيات وبحث الأعضاء وتغطية حالات عدم وجود نتائج.
4. تصحيح تمييز العنصر النشط في الشريط السفلي وإقرار خريطة واضحة للتبويب النشط في كل شاشة.
5. تعديل «إدارة رابط الانضمام» ليعرض حالة الرابط ولا ينفذ التجديد مباشرة.
6. إظهار إدارة الرابط للمدير بعد قفل الاتفاق مع إبقاء pause/revoke متاحين، ومنع create/rotate/resume وفق قيود الخادم.
7. إخفاء سجل العمليات الإداري من حساب المشارك.

### الدفعة الثانية — توحيد تجربة العضوية
8. جعل «استقبال الأعضاء» نقطة الإدارة المركزية للأعضاء والدعوات الخاصة وطلبات الانضمام.
9. إبقاء الفرق ظاهراً بين الدعوة الخاصة ورابط الانضمام العام الذي ينشئ طلباً للمراجعة.
10. تقليل أدوات إدارة العضوية المعروضة في صفحة نجاح الإنشاء وتحويلها إلى اختصارات قليلة.
11. مراجعة النصوص المتكررة حول الرابط، والنسخ، والمشاركة، والإيقاف، والتجديد والإبطال.
12. إضافة تأكيد صريح للأفعال ذات الأثر، خصوصاً تجديد الرابط وإبطاله.

### الدفعة الثالثة — استكمال أدوات المدير
13. اتخاذ قرار بشأن واجهة تعديل بيانات الجمعية قبل القفل.
14. اتخاذ قرار بشأن واجهة إضافة/إزالة الأسهم وإزالة العضو، لأن عمليات البيانات موجودة دون مسار مستخدم ظاهر في الشاشات الحالية.
15. توحيد مواضع الوصول إلى سجل التدقيق دون إزالة وظائفه.
16. الحفاظ على فصل شاشة الأقساط عن سجل الاستلام، وغرفة القرعة عن تاريخ النتائج.

### الدفعة الرابعة — تنظيف الربط والاختبارات
17. إزالة أو إعادة ربط group-tab وbioToggle بعد تأكيد عدم وجود اعتماد ديناميكي عليهما.
18. إزالة استدعاءات header() الفارغة بعد توحيد مصدر العنوان.
19. إضافة labels وARIA المناسبة لحقول البحث والنماذج التي تحتاجها.
20. توسيع اختبارات العقد لتشمل سلوك العناصر لا مجرد وجود handler.
21. تشغيل اختبارات Node ثم اختبارات Supabase المحلية المعزولة بعد الإصلاحات، وعدم لمس قاعدة الإنتاج.

### الدفعة الخامسة — اعتماد النشر والجودة البصرية
22. اختبار جميع الشاشات بحساب مدير وحساب مشارك، وحالات اتفاق مفتوح ومقفل، مع بيانات اختبار معزولة.
23. اختبار الجوال وسطح المكتب بعد الإصلاح، والتحقق من الشريط السفلي والقوائم والنماذج والحوارات.
24. تحديد خدمة Render الرسمية لفرع SAHM-SUPABASE وتوثيق رابطها.
25. بعد التأكد من استخدام الخدمة الثانية وعدم الحاجة إليها، اتخاذ قرار مستقل بشأن الإبقاء عليها أو إيقافها؛ لا حذف تلقائي.

## 12. ترتيب التنفيذ الموصى به

التسلسل الأفضل هو: **الدفعة الأولى، ثم الثانية، ثم الثالثة وفق قرار المنتج، ثم الرابعة، ثم الخامسة**. لا يوصى بتنظيف CSS إضافي أو دمج شاشات أو إزالة مسارات تاريخية قبل إتمام إصلاحات التفاعل واختبارها بصرياً ووظيفياً.

## 13. القرار المطلوب قبل التنفيذ

هذا التقرير ينهي التدقيق ويقدم قائمة الإصلاحات، لكنه لا يمنح إذناً تلقائياً بتطبيقها. أهم قرارين قبل البرمجة:
1. اعتماد أن «جمعيات أديرها» و«جمعيات أشارك فيها» وجهتان واضحتان منفصلتان للمستخدم، مع قائمة مشتركة داخلياً.
2. تحديد ما إذا كانت واجهة تعديل الجمعية وإدارة الأسهم/إزالة العضو مطلوبة في الإصدار الحالي، أم تبقى عمليات داخلية غير معروضة حتى مرحلة لاحقة.

بقية إصلاحات الدفعة الأولى مدعومة بمشكلات واضحة في التنفيذ الحالي، ويمكن تنفيذها بعد اعتماد قائمة الإصلاحات.
